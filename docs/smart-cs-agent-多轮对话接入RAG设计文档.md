## 1. 背景与问题

### 现状（实现前；已由 E1 + 仅多轮入口解决）

| 入口 | 行为 |
|------|------|
| 曾有 `mode=faq` | 无路由直搜（已移除子命令） |
| 曾有 `mode=chat` 无检索 | 政策题无上下文（已接路由+条件 RAG） |
| Tools | 订单/工单/额度/天气/MCP 由 Agent 按需调用 |

### 问题

多轮要同时服务「政策知识」与「实时 Tool」。若**每轮都向量检索**（教程朴素 RAG），实现简单，但：

- 查 ORD002 / 问天气也打 Embedding，浪费且可能噪声；  
- 与企业常见「先分通道」不一致，实习讲述偏弱。

若**完全不检索**（当前 chat），政策演示直接失败。

### 本设计立场

采用**企业常见做法**：**先理解用户意图（含关键信息/检索词），再决定是否走向量库**；需要时才 `retrieve`，再交给现有 Agent + Tools。

> 教程 chapter10 = 每次必搜的教学 RAG；本仓默认入口 = 路由 + 条件 RAG + Tools（合仓后的正确形态）。

## 4. 用户入口与主流程

### 入口

```text
uv run python -m app.main [--no-mcp]
# PyCharm：Run app/main.py
```

### 目标主流程（每轮）

```text
用户原文 raw
    │
    ▼
┌───────────────────────┐
│ 1. 轻量解析             │  规则抽实体：ORD/T/U 编号、城市名等（可选）
│    + 检索词候选         │  可保留原文作 search_query 初值
└───────────┬───────────┘
            ▼
┌───────────────────────┐
│ 2. 意图分析（路由）      │  输出结构化结果（见契约）
│    模型小调用 或 规则优先 │  need_rag / intent / search_query
└───────────┬───────────┘
            ▼
     need_rag == true ?
        │是              │否
        ▼                ▼
   retrieve(search_query)   仅传 raw
   （失败→当无命中）         │
        │                │
        ▼                │
   拼装 raw + 知识库片段      │
        │                │
        └────────┬───────┘
                 ▼
         agent.ainvoke（现有 Tools）
                 ▼
              打印回复
```

**要点**：向量库不是每轮必经；**路由说要，才搜**。

## 5. 分期交付

| 步 | 交付 | 说明 |
|----|------|------|
| **E1（本期必做）** | **规则优先 + LLM 补判** 的路由；条件检索；降级；可观测日志 | 企业骨架，改动可控 |
| E2 | 查询改写强化、模糊政策漏检评测集 | 路由不准时再加 |
| E3 | Hybrid / Rerank / RAG-as-Tool | 另开设计 |

### E1 内部分层（实现顺序）

1. **硬规则短路径**（不调用分类模型）：命中订单/工单/账号号形态，或强天气意图词 → `need_rag=false`。  
2. **其余句子** → **一次结构化 LLM 调用**（意图分析）：是否需要知识库、建议 `search_query`（可从原文提炼关键词/短查询）。  
3. `need_rag=true` → `retrieve(search_query or raw)` → 拼装 → Agent。  
4. `need_rag=false` → 原文进 Agent（靠 Tools/闲聊）。

这样既符合「先分析再决定是否向量匹配」，又对 ORD/天气等**最稳路径不依赖分类模型**，降低漏检与误搜。

## 6. 方案与选型

### 选定：意图路由 + 条件 RAG（否决「每轮必搜」）

| 点 | 选择 | 原因 |
|----|------|------|
| 总策略 | 先路由，再决定是否向量检索 | 企业常见；契合「知识 vs 业务 vs 实时」分通道 |
| 检索词 | 路由产出 `search_query`（关键词/短句），否则回退原文 | 对齐「拆/提炼后再匹配」，非盲目整句可接受回退 |
| 检索位置 | 仍在 **Agent 外** | 与现 prompt「据上下文答政策」一致；避免 Agent 忘调 retrieve |
| 硬规则 | ORD/T/U、天气等先短路 | 最小成本、行为稳，友好维护 |
| LLM 路由 | 结构化输出（见契约） | 政策/发票/权限等语义题规则盖不全 |
| 无命中 | 不硬塞「无相关片段」 | 避免干扰后续 Tool |
| 失败 | 路由或 Milvus 异常 → 当 `need_rag=false` 或空 hits，并提示 | 不挡多轮 |

### 明确不选（作默认）

| 方案 | 原因 |
|------|------|
| 每轮必搜（旧稿 R1） | 与产品决策不符；噪声与成本差 |
| 仅规则、无 LLM 路由 | 政策说法一变就漏，不够「分析」 |
| 仅 RAG Tool、无前置路由 | 易忘调；与「上下文」约束叠床架屋 |
| 一上来 Hybrid/Rerank | 超一期范围 |

### 与教程的关系

| | 教程 chapter10 | 本设计 |
|--|----------------|--------|
| 是否每次检索 | 是 | **否**，路由后才检索 |
| 查询 | 整句 embedding | 优先 `search_query`，可回退整句 |
| Agent | 常无 Tool | 本仓有 Tools，故必须路由 |

## 8. 契约

### 8.1 路由结果 `RouteResult`（逻辑字段，实现可用 TypedDict/Pydantic）

| 字段 | 类型 | 说明 |
|------|------|------|
| `intent` | 枚举字符串 | 建议：`knowledge` / `order` / `ticket` / `account` / `weather` / `mcp_news` / `chitchat` / `unknown` |
| `need_rag` | bool | 是否调用向量检索 |
| `search_query` | str | 供 embedding 的短查询；可为空则用原文 |
| `reason` | str | 短说明，便于日志（可对用户隐藏） |

**判定约定（E1）**

| 条件 | need_rag | 典型 intent |
|------|----------|-------------|
| 含 `ORD\d+` / `T\d+` / `U\d+` 且像查询状态/额度 | false | order/ticket/account |
| 强天气（「天气」「气温」「下雨」+ 城市等） | false | weather |
| 套餐/退款/发票/权限/超额/数据保留等政策产品 | true | knowledge |
| 新闻/舆情/邮件 | false | mcp_news（交给 MCP tools） |
| 不确定 | **true（偏好召回）** | unknown；**已拍板：默认 need_rag=true**，避免政策题再「无上下文」 |

> **已拍板（2026-09-14）**：不确定意图时 `need_rag=true`（偏检索）。

### 8.2 LLM 路由提示（要点，非最终文案）

- 只输出结构化字段，禁止长作文。  
- `search_query`：抽 3～30 字关键问法，去掉「帮我问问」等废话。  
- 订单号天气等若已由规则处理，可不调用 LLM。

### 8.3 拼装（仅 need_rag 且 hits 非空）

```text
{raw}

【知识库检索，仅供产品/政策问答；订单/工单/额度/天气/新闻请用工具，可忽略本段】
{format_hits_as_context(hits)}
```

### 8.4 CLI

- 默认 chat 走路由管线。  
- 已移除单次 `faq` 子命令；知识库问答一律在多轮内按路由检索。  
- 可选以后：`--rag always|route|off`；E1 可不做。

## 9. 数据与记忆模型

| 类型 | 本设计 |
|------|--------|
| 路由结果 | 每轮瞬时，可打日志；不落长期库 |
| 检索片段 | 仅附在**本轮** user 消息 |
| 会话记忆 | 非本设计；步②后注意历史里携带的检索块撑 token |

概念封印：路由 ≠ 用户画像；检索 ≠ 短期记忆。

## 11. 验收与手测（L2）

前置：Milvus + ingest；`app.main --no-mcp`。

1. 超额政策 → 日志 `need_rag=true` → 回答有口径。  
2. ORD002 → 日志 `need_rag=false` → 退款审核中。  
3. 北京明天天气 → `need_rag=false` → 有预报。  
4. 发票/退款/权限各一问 → 需检索且能答或明确依据不足。  
5. 停 Milvus 问政策 → 降级不崩；再问 ORD 仍可。  
6. 多轮再问超额（Milvus 正常时）→ 有检索或合理回答（回归；原 `faq -q` 已并入多轮）。
